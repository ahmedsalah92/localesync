# LS-13 — Telemetry + paid-intent capture

Issue: [LS-13](https://linear.app/brilliant-solutions/issue/LS-13). Definitions: Linear doc "LS-13 —
Definitions". Design: the `Pro Stub` component set; its instances are `350:1404` (Matrix), `350:1420`
(Report), `350:1412` (Translate) and `351:1411` (Sync), in file `UlcEw6zdZzpIpxqrBz4X53`.

**What this builds:**
- **Paid intent**, the willingness-to-pay gate, with no network access. Each of the four Pro stubs
  opens the waitlist in the browser through `figma.openExternal`. The URL's UTM parameters let the
  landing page's Umami tell the four apart.
- **A typed activation-event emitter**, called once at each core action's success point. Phase 1
  sends events to a no-op sink in production and a console sink in dev.

**Decided with the product owner (2026-09-26):**
- **D1 — UTM scheme:** `utm_source=figma&utm_medium=plugin&utm_campaign=pro-waitlist&utm_content=<pillar>`.
- **D2 — URL placeholder:** the waitlist URL doesn't exist yet. `WAITLIST_URL` holds the placeholder
  `https://example.invalid/waitlist`. A **release-only** check, `npm run check:release`, fails while
  the placeholder is still present. It's run before publishing, never in everyday CI (D6).
- **D6 — Where the guard runs:** in a release step only. `npm run build` and CI stay green while the
  placeholder is in place.
- **D3 — Stub behaviour and copy:** the stub is one band-sized button. Its tooltip and `aria-label`
  say it's coming in Pro, that it opens the browser, and that the plugin sends no data.
- **D4 — The event table:** as in §2.2, success-only, with fixed-value properties.
- **D5 — First-run memory:** "install" and "first scan" are remembered in main-thread
  `clientStorage`.

**Out of scope** (per the issue):
- a paywall or licensing (Phase 2);
- a live network collector, a deferred upgrade whose path is documented in §2.5;
- Community-listing privacy copy (LS-16).

### §1.2 Amended: `src/common/messages.ts` (LS-2)

```ts
import type { ProPillar } from './pro';

// UI → main, commands (outcome on progress/error)
export interface OpenWaitlist extends Envelope<'open-waitlist'> {
	pillar: ProPillar;
}
export interface TelemetryMark extends Envelope<'telemetry-mark'> {
	flag: 'first-scan';
}
// UI → main, request
export type TelemetryStateRequest = Envelope<'telemetry-state-request'>;
// main → UI, response
export interface TelemetryState extends Envelope<'telemetry-state'> {
	firstLaunch: boolean;   // true exactly once per user: this request marked the plugin installed
	firstScanDone: boolean;
}
// RequestResponse gains: 'telemetry-state-request': TelemetryState (+ RESPONSE_TYPE entry)
```

- **Allow-lists:** all four types go into the `Record` allow-lists, and each gets one fixture.
- **Round-trip scaffold:** `PROBED_COMMANDS` gets `'open-waitlist': false`, because the real handler
  opens a browser tab and must never be probed. It also gets `'telemetry-mark': false`, because the
  real handler writes the user's `clientStorage`.

export type ProPillar = 'matrix' | 'report' | 'translate' | 'sync';

### §1.4 Produced: `src/ui/telemetry.ts` (UI only)

```ts
export type TelemetryEvent =
	| { name: 'install' }
	| { name: 'first_scan'; kind: 'extract' | 'overflow' }
	| { name: 'overflow_scan_run'; scope: 'page' | 'selection' }
	| { name: 'pseudoloc_applied'; expansion: 30 | 40 | 50 }
	| { name: 'rtl_applied'; scope: 'page' | 'selection' }
	| { name: 'preview_used' }
	| { name: 'export_performed'; format: 'json' | 'ios' | 'android' };

export type Sink = (event: TelemetryEvent) => void;
export const noopSink: Sink;
export const consoleSink: Sink;            // console.log('[telemetry]', event)
/** THE one line to change for a real collector (§2.5). */
export const SINK: Sink = import.meta.env.DEV ? consoleSink : noopSink;
export function track(event: TelemetryEvent, sink: Sink = SINK): void;
```

- **Test seam:** the `sink` parameter exists only so tests can inject a spy. Call sites never pass
  it.
- **First scan:** `src/ui/telemetry.ts` also exports `markFirstScan(kind)`, which has four steps:
  1. it does nothing unless the `firstScanDone` it holds is false;
  2. it fires `track({ name: 'first_scan', kind })`;
  3. it sends `telemetry-mark`;
  4. it sets its own flag, so the event fires once per session even before the main thread
     persists it.
- **Where the first-scan decision lives:** in a pure helper, `firstScanAction(done: boolean)`, which
  returns `'fire' | 'skip'`.

### §1.5 Produced: main thread, `src/main/telemetry.ts`

- **What it stores:** `{ installed: boolean; firstScanDone: boolean }` in `clientStorage` under
  `localesync:telemetry:v1`. Anything malformed is read as `{ false, false }`, the same way LS-12
  treats its store as a cache.
- **`telemetry-state-request`:**
  1. read the stored flags;
  2. set `firstLaunch = !installed`;
  3. write `installed: true`;
  4. `respond`.

  If the write is rejected, it still answers with the flags it read, and warns in dev. Telemetry
  never breaks the plugin.
- **`telemetry-mark`:** writes `firstScanDone: true` and answers `progress`. A write failure answers
  `progress` as well: best-effort, never an error the UI must handle.
- **`open-waitlist`:** calls `figma.openExternal(waitlistUrl(msg.pillar))`, then `progress`. If it
  throws, the answer is `error` `internal`.
- **Registration:** registered from `main.ts` beside the feature handlers.

## §2 Resolved Defaults

### §2.1 Waitlist URL and the release guard (D1, D2)
- The URL has no user id, file id or version: it is identical for every user, so there's no
  personal data.
- **Release guard (D6):** a new `scripts/check-release.mjs`, run as `npm run check:release`.
  - It builds for production if `dist/` is missing or stale, then scans `dist/main.js` and
    `dist/ui.html` for `example.invalid`. It exits non-zero, naming the file, while the placeholder
    is present.
  - It is **not** part of `npm run build` or the CI workflow, so everyday CI stays green.
  - It is the documented pre-publish step, listed in CLAUDE.md/AGENTS.md "Commands" (the twins stay
    identical, which `check:docs` enforces).
  - Development builds and Vitest are unaffected.
- **When the real URL exists:** it's a one-line change to `WAITLIST_URL`. The guard then passes with
  no other edit.

### §2.2 Activation events (D4)

| Event | Fires once when… (success only) | Call site |
|---|---|---|
| `install` | the launch-time `telemetry-state` answers `firstLaunch: true` | the shell, once at mount |
| `first_scan` | the first extraction or overflow scan **completes** for this user | `markFirstScan('extract')` in ExtractPanel's result handler; `markFirstScan('overflow')` in OverflowPanel's result handler |
| `overflow_scan_run` | an overflow scan completes and was not stopped | OverflowPanel, beside `first_scan` |
| `pseudoloc_applied` | a Pseudo-loc apply's terminal progress arrives | PseudoPanel, where it dispatches `applied` |
| `rtl_applied` | an RTL apply succeeds | RtlPanel, where it dispatches `applied` |
| `preview_used` | a Preview language apply succeeds (not an edit, not a re-apply after a failed edit) | PreviewPanel, when an `apply` op's progress lands |
| `export_performed` | the Export dialog starts a download | ExportModal's `onDownload` |

- **No personal data:** every property value comes from a closed literal union. There is no free
  text, key, layer name, language code or id anywhere.
- **Failure and cancellation:** a failed or cancelled action emits nothing.

### §2.3 The Pro stub (`src/ui/shell/ProStub.tsx`, D3), replacing `FooterStub`
- **Layout:** one `<button type="button">` filling a `BAND_HEIGHT` band.
  - **Left:** `PRO_LABEL[pillar]` (text/default, the UI3 body style), then a **Pro** badge
    (text/brand on a brand border, the UI3 badge treatment).
  - **Right:** the ↗ `ArrowIcon` in icon/secondary.
  - Tokens only, with the same padding as today's `FooterStub`.
- **Tooltip and label:**
  - The existing `Tooltip` shows **"Coming soon in Pro. Opens the waitlist in your browser.
    LocaleSync doesn't send any data from the plugin."**
  - `aria-label`: `${PRO_LABEL[pillar]} — ` followed by the same text.
- **Click:** `send<OpenWaitlist>({ type: 'open-waitlist', pillar })`. There's no confirm, no modal,
  and no in-plugin "Pro" screen.
- **Placement:**
  - OverflowPanel → `matrix` and ExtractPanel → `report`, wherever each shows its footer today
    (their `hasFooter` rules are unchanged);
  - PreviewPanel → `translate`;
  - RtlPanel gains a footer band with `sync`, as the canvas shows (`351:1411`);
  - PseudoPanel gets none.
- `FooterStub.tsx` is deleted once nothing imports it.

### §2.4 Launch
The shell sends `telemetry-state-request` once when it mounts. That's safe since LS-34, because the
shell and all panels mount once. It fires `install` if `firstLaunch` is true, and hands
`firstScanDone` to the telemetry module.

### §2.5 Upgrade path (documented, not built)
1. **A real collector** means replacing `SINK` in `src/ui/telemetry.ts` with a sink that posts
   events, which is the one line D4 promises.
2. **The network change that requires** is to allowlist exactly one collector host in the manifest,
   with a written `reasoning`. First spike whether the host accepts requests from the UI iframe's
   `null` origin (agent-guidelines §2).
3. **Paid intent needs no change.** It stays a browser handoff.

### §3.2 Release guard
- With the placeholder in place:
  - `npm run build` **passes**, so CI is unaffected;
  - `npm run check:release` **fails**, naming `example.invalid` and the file it's in.
- To check the guard, temporarily set a real-looking `WAITLIST_URL`: `check:release` then passes.
  Restore the placeholder before committing.
- A Vitest test covers the scan function if it is factored as a pure `findPlaceholder(text): boolean`
  in a `.mjs` helper that the test can import. Otherwise the manual run above is the proof.

### §3.3 In Figma, by hand (`npm run dev`)
1. Click each of the four stubs. The browser should open
   `https://example.invalid/waitlist?utm_source=figma&utm_medium=plugin&utm_campaign=pro-waitlist&utm_content=<pillar>`
   with the right pillar. The page itself won't resolve, as expected.
2. Hover a stub: the tooltip text should read exactly as in §2.3.
3. In the dev console, each success action logs one `[telemetry]` event with the table's
   properties. Failures and cancellations log nothing.
4. Clear the stored telemetry flags (a dev harness button, **Clear telemetry flags**, which deletes
   the `clientStorage` key), then reopen the plugin. `install` logs once. Reopen again: no `install`.
   The first completed scan logs `first_scan` once, ever.
