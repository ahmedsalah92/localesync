# LS-21 — Resizable plugin window: mechanism, clamping, size persistence

**Epic:** Foundation · **Complexity:** Med · **Parent:** LS-5 · **Blocked by:** — (LS-5 closed)

The window the shell lives in. LS-5 shipped the default size; this issue makes it draggable,
enforces a floor, and remembers what the user chose.

The mechanism is **edge-drag**, decided 2026-09-01: corner-drag is not a native Figma affordance,
and the custom grip removed on kit-rule grounds *was* the mechanism, not a decoration. A plugin
implements resizing by tracking pointer movement and calling `figma.ui.resize()`. The one message
type this needs was approved on LS-2 the same day.

**Units convention, load-bearing throughout.** Figma always draws ~40px of its own window chrome
above the plugin iframe and `showUI` cannot suppress it. Every number in this spec is an **iframe**
number — what `figma.ui.resize` receives — matching `SHELL_DEFAULT_SIZE`. The on-screen window is
40px taller in each case.

| | On screen | Iframe (this spec) |
|---|---|---|
| Default | `400×720` | `400×680` — `SHELL_DEFAULT_SIZE` |
| Minimum | `340×480` | `340×440` — `SHELL_MIN_SIZE` |

---

## 1. Contracts

Upstream types are referenced, never redefined (`docs/agent-guidelines.md` §4). LS-21 consumes
`SHELL_DEFAULT_SIZE` and `BAND_HEIGHT` from LS-5, and `send` / `on` from LS-2's bridges.

### 1.1 Size constants and the shared clamp

```typescript
// src/common/shell.ts — LS-5 owns the file; LS-21 adds to it. Env-neutral, ambient-free.
export interface WindowSize {
	width: number;
	height: number;
}

/**
 * Iframe units, chrome-subtracted — the on-screen minimum window is 340×480. Figma draws ~40px of
 * its own chrome above the iframe and `showUI` exposes no way to suppress it, so this is the
 * number `figma.ui.resize` receives. Same convention as SHELL_DEFAULT_SIZE.
 */
export const SHELL_MIN_SIZE = { width: 340, height: 440 } as const;

/**
 * Rounds each axis to an integer, then floors it at SHELL_MIN_SIZE. No maximum — Figma clamps to
 * the viewport itself. Pure. The single clamp behind all three call sites: the drag handler, the
 * resize-window handler, and the launch read.
 *
 * A non-finite axis falls back to that axis's SHELL_DEFAULT_SIZE value. isWindowSize still rejects
 * non-finite stored values; the guard and this defensive fallback are belt and braces.
 */
export function clampWindowSize(size: WindowSize): WindowSize;

/** Guard for the clientStorage read: an object with two finite numbers, nothing else. Pure. */
export function isWindowSize(x: unknown): x is WindowSize;
```

## 2. Resolved Defaults

Every value below is fixed. No implementer choices remain.

### 2.1 The minimum is 340×440, and why it is not 480

`design.md` records the minimum as `340×480` in **window** units, in the same entry that records
the default as `400×720` — and LS-5 already converted that default to the iframe's `400×680`. The
minimum was never converted because until now nothing consumed it.

That the entry is already reasoning in iframe units is checkable from its own arithmetic: it claims
"~560px of list after the control bar" at default size, and `680 − 40 − 40 − 40 = 560` while
`720 − 40 − 40 − 40 = 600`. Taking `480` literally would put the two constants in `src/common/shell.ts`
in different units and make the minimum window 40px taller than designed.

At `440`: `440 − 40 (tab) − 40 (control) − 40 (summary) = 320` of rows footerless, `280` with a
footer — exactly five 56px rows.

### 2.2 Grip anatomy and placement

| | Corner | Bottom edge |
|---|---|---|
| Axes | width **and** height | height only |
| Box | `position: fixed; right: 0; bottom: 0; width: 16px; height: 16px` | `position: fixed; left: 0; right: 16px; bottom: 0; height: 4px` |
| Cursor | `nwse-resize` | `ns-resize` |

Both carry `touch-action: none` (so a touch/trackpad gesture cannot steal the pointer mid-drag) and
**no background, border, or colour token of any kind**. The edge strip stops 16px short of the
right so the two hit zones never overlap.

**No right edge.** The scrollbar runs it, and the corner already yields both dimensions. Width was
the binding constraint (four controls in one bar) and the corner delivers it.

**No drawn grip.** It is the only option that would need an explicit kit-rule exception, and it
spends a visible element in an already dense panel. The `Tooltip` hex exception was forced — UI3
publishes no tooltip set; this one is not.

`ResizeHandle` mounts once, from `ShellBody`, as a sibling of the panel container — the same place
and the same shape as the existing `{import.meta.env.DEV && <DevHarness />}` line. Because it is
`position: fixed`, it escapes the shell's `overflow: hidden` flex column and sits at the iframe's
bottom edge regardless of which panel is mounted.

### 2.3 Drag math is absolute, not incremental

At `pointerdown`, capture how far the cursor sits from the iframe's bottom-right, then recompute
the size from the cursor on every move:

```
pointerdown:  grabOffsetX = window.innerWidth  − event.clientX
              grabOffsetY = window.innerHeight − event.clientY
              element.setPointerCapture(event.pointerId)

pointermove:  width  = event.clientX + grabOffsetX      // corner only; edge holds window.innerWidth
              height = event.clientY + grabOffsetY
```

This works because the iframe's **top-left is pinned** during a bottom or bottom-right resize, so
`clientX` is measured from a fixed origin and is the width minus the grab offset.

Absolute rather than delta accumulation because the loop is not local — the iframe cannot resize
itself, so every visual update is a round trip through the bridge, and a locally-accumulated size
would diverge from the real one and never reconverge. Three concrete failures it avoids: at the
viewport limit Figma grants less than we asked for and a local counter would produce a dead zone
until it unwound; under lag the grip would render away from the cursor; and any dropped message
would be permanent error. Re-reading `window.innerWidth/innerHeight` each gesture makes all three
self-correcting within one frame.

Capturing `grabOffset` rather than assuming a grab point also means grabbing the middle of the
16×16 corner does not jump the window 8px on the first move — the common `clientX + 16` shortcut
does exactly that.

`releasePointerCapture` on both `pointerup` **and** `pointercancel`; the gesture state ref is
cleared in the same place.

### 2.4 Send on every pointermove; one correlation id per gesture

**Rate.** Send on every `pointermove` while captured. No `requestAnimationFrame` coalescing, no
time throttle. Browsers already deliver at most one `pointermove` per frame — the un-coalesced
stream is only reachable via `getCoalescedEvents()`, which we never call — so a throttle would drop
almost nothing and add up to a frame of lag. Latency here is not a smoothness question: the cursor
stays inside the iframe only because the edge chases it, and enough lag on an outward drag lets the
pointer exit the iframe and kill the gesture mid-drag.

**Ids.** One id per drag gesture, reused for every move of that gesture. The first `pointermove`
calls `send()` with no id and keeps the id it returns; every subsequent move passes that id back —
the same mechanism `overflow-scan-cancel` uses to address an exchange already in flight. A drag is
one exchange, so the id says something true in a message log; minting per move would spend ~200 ids
per resize on the shared `ui-<n>` counter for an id nothing correlates against.

### 2.5 Clamp: round then floor, at three call sites

```
clientX + grabOffset  →  Math.round  →  Math.max(SHELL_MIN_SIZE.axis, …)  →  send / resize
```

Round **before** clamping, so the clamp sees the exact integer that will be sent. Integers only:
`figma.ui.resize` is documented with a 70×0 floor and says nothing about fractional values, and
`clientX` on a scaled display is fractional. No maximum — Figma clamps to the viewport and a
hard-coded ceiling would fight it.

The two clamps are not redundant; they do different jobs, and the LS-21 success criterion names
both paths:

| Clamp | Job | Symptom if removed |
|---|---|---|
| UI, before `send` | Stops the grip tracking a cursor the window cannot follow | Drag past the minimum, the window stops, the cursor keeps going, leaves the iframe, gesture dies |
| Main, before `figma.ui.resize` | The actual enforcement — `resize()` accepts anything ≥70×0 | The minimum becomes a suggestion |

Both call the same `clampWindowSize()`, which is what makes "verified from both the UI handler and
a direct main-side call" a unit test rather than a click-through.

### 2.6 Persistence: one key, one write per drag

**Key** `localesync:window-size:v1` — LS-4's `localesync:<thing>:v1` convention, deliberately
outside the `PLUGMA_` namespace. Plugma's own `PLUGMA_PLUGIN_WINDOW_SETTINGS_DEV` / `_PREVIEW`
carry dev-toolbar and browser-preview state, are keyed separately, and will not carry a user's size
in the shipped plugin. We neither read nor write them.

**Value** the `WindowSize` object stored directly — `clientStorage` structured-clones, so no
`JSON.stringify`, matching how LS-4 stores its manifest.

**Timing** a main-side **trailing debounce of 250 ms**: each `resize-window` clears and resets the
timer; the timer writes the last clamped size. One drag produces one write instead of ~200.
`@figma/plugin-typings` declares `setTimeout(callback, timeout): number` and
`clearTimeout(handle: number): void` as globals, so this compiles under `lib: ["ES2020"]` with no
DOM (verified against the pinned `1.130.0`). Note the handle is a `number`, and `timeout` is a
required argument.

**Write failure** is non-fatal: a rejected `clientStorage.setAsync` logs a warning, matching the
`console.warn` failure pattern around `restoreAll()` in `main.ts`, and does not undo the resize.

Two paths that look plausible and are both closed:

- **On `pointerup`** would need a second message type. The LS-2 approval is scoped to
  `resize-window` only; a second type needs a new approval.
- **On `figma.on('close')`** cannot work. The close handler runs synchronous code only
  (`agent-guidelines.md` §2) and `clientStorage.setAsync` is async, so the write would never
  complete.

**Known bounded loss, recorded not fixed.** `figma.closePlugin()` cancels pending timers, so
closing the plugin within 250 ms of releasing a drag loses that one resize; the next resize
persists. There is no rescue path, for the reason immediately above.

### 2.7 Launch order

```typescript
// src/main/main.ts
const size = await loadWindowSize();                                    // BEFORE showUI
figma.showUI(__html__, { ...size, themeColors: true, title: 'LocaleSync' });
// … restoreAll(), registerCloseHandler(), and the existing registrars, unchanged
registerWindow();
```

The window paints exactly once, at the restored size. `loadWindowSize` costs one `clientStorage`
read, which is why it can sit in front of `showUI` without a perceptible delay; `restoreAll()` is
the expensive one and stays where LS-4 put it, after `showUI`.

`loadWindowSize` falls back to `SHELL_DEFAULT_SIZE` on a read failure **and** on a value that fails
`isWindowSize`, then passes whatever it has through `clampWindowSize()`. The re-clamp is not
belt-and-braces: a size written by an older build, or a store edited by hand, must not open the
window under the minimum.

### 2.8 Scroll clearance is stacking order, not padding

`design.md` and the Linear issue both attribute clearance to 16px `padding-bottom` on the scroll
container, "so the scrollbar terminates above the corner zone." **Padding does not do that.** A
scrollbar spans its container's whole padding box; padding moves the content up, not the track. The
thumb still reaches the bottom-right corner.

What actually keeps the corner drag off the scrollbar is paint order: `ResizeHandle` is
`position: fixed`, so it paints above the scroll container and hit-tests first. Nothing else in the
shell is positioned, so no `z-index` is needed.

Consequences:

- **`ResultsList` is unchanged.** Its existing `paddingBottom: var(--spacer-3)` when
  `hasFooter === false` stays, reclassified as end-of-list spacing. It is also already generalized
  past All Nodes and Scanning — it covers every footerless panel, which is the per-shell exception
  list LS-5 §2.2 deliberately replaced with a prop.
- **`design.md` → Window dimensions → Scrollbar clearance needs a one-line correction**, the same
  class of correction that entry already carries for the "native corner cursor" that did not exist.
- **The success criterion needs a precision fix** (§5, item 2) — as written it describes a state
  that will never be observed whether or not the implementation is correct.

### 2.9 Union bookkeeping

`messages.test.ts` asserts one fixture per type *and* `fixtures.length === ALL_TYPES.length`, with
`ALL_TYPES` kept deliberately independent of `messages.ts`. So three files move together:

| File | Change |
|---|---|
| `src/common/messages.ts` | `ResizeWindow` interface, `UiToMain` member, `UI_TO_MAIN_TYPES` entry |

No `RequestResponse` entry, no `RESPONSE_TYPE` entry, no `MainToUi` addition, no
`messages.type-check.ts` case — nothing about this type is subtle enough to earn a negative test.
Final count **18**: 12 `UiToMain`, 6 `MainToUi`.

### 3.3 In Figma — production `npm run build`

Repeat every check in §3.2 against the built plugin. This is a separate run, not a formality:
Plugma injects its runtime and rewrites `figma.ui.resize(...)` → `customFunctions.customResize(...)`
in the **dev** config only — the production plugin list is `[replacePlugmaTesting,
processEnvMigrationWarning]`, so `figma.ui.resize` stays literal. The two builds are genuinely
different code paths for the one API this issue exists to call.

**The dev-only symptom to recognise:** a window that snaps to **200×40** is Plugma's `customResize`
honouring its stored `minimized` flag, not our clamp. It cannot occur in the built plugin. Do not
debug it as a LocaleSync bug.

**Run:** `npx tsc -b && npx eslint . && npm test && npm run check:docs`, then `npm run dev`, then
`npm run build`.

**Review focus:** the launch-order path (§2.7) and the persistence debounce (§2.6). A `showUI`
called before the `clientStorage` read still *works* — it just flashes, which is easy to miss on a
fast machine and is the whole point of the "no visible jump" criterion. And a persist call left on
the per-move path will pass every functional check while writing to `clientStorage` two hundred
times per drag.

## 4. API pins

Per `docs/agent-guidelines.md` §2 — not repeated here. LS-21 touches two main-thread surfaces
(`figma.ui.resize`, `figma.clientStorage`) and one iframe surface (Pointer Events).

> **Two pins to add to §2.**
>
> **`figma.ui.resize(width, height)` enforces a floor of 70×0 and nothing else.** `showUI`'s own
> minimums are width 70, height 0. Any product minimum is the plugin's to enforce; `resize()` will
> accept `340×12`. The method takes **iframe** dimensions — Figma's ~40px window chrome sits above
> and outside them. Verified against the live plugin docs 2026-09-06.
>
> **`setTimeout` / `clearTimeout` are declared globals on the main thread.**
> `@figma/plugin-typings` (pinned `1.130.0`) declares `setTimeout(callback: Function, timeout:
> number): number` and `clearTimeout(handle: number): void`, so timers compile under
> `lib: ["ES2020"]` with no DOM. The handle is a plain `number`, and `timeout` is required, not
> optional. **`figma.closePlugin()` cancels every pending timer** — a debounced write that has not
> fired when the plugin closes is lost.

## 5. Carried forward

1. **`docs/agent-guidelines.md` §1 folder map needs two rows** —
   `src/main/window.ts   LS-21  window size: restore, clamp, persist` and
   `src/ui/shell/ResizeHandle.tsx  LS-21  edge + corner resize grip`. The shell folder stays LS-5's;
   LS-5 §0 already assigns this file's subject matter to LS-21, and the map is what §4 consults for
   ownership, so it has to say so.
2. **Precision fix — the range criterion.** *"The window resizes via edge-drag … between `340×480`
   and the viewport limit"* is ambiguous about which box is measured, so a reviewer can verify the
   wrong one. Proposed: *"between a `340×480` on-screen window (`resize(340, 440)` at the iframe)
   and the viewport limit."*
3. **Precision fix — the scrollbar criterion.** *"The scrollbar … terminates above the corner hit
   zone"* describes a state that never occurs (§2.8). Proposed: *"In a footerless panel scrolled to
   the bottom, a pointerdown inside the 16×16 corner zone starts a resize and does not move the
   scroll position."*
4. **Scope deletion on the issue.** The "16px `padding-bottom` on the All Nodes and Scanning
   shells" requirement is already built and already generalized (§2.8). It should come off the
   requirement list rather than be re-implemented as a per-shell exception.
5. **`docs/design.md` → Window dimensions** needs the §2.8 clearance correction and the
   `340×480` → `resize(340, 440)` conversion noted alongside the existing "Shell framing
   convention" sub-entry.
6. **Gesture-boundary persistence, if the 250 ms loss window ever matters.** The per-gesture
   correlation id (§2.4) makes it detectable main-side when a *new* drag begins, which would let
   the previous gesture's size flush immediately instead of on the timer. It does not help the
   close-during-debounce case, so it is not worth building now.
7. **`figma.ui.reposition` / docking** stays out of scope. Left-edge resizing depends on it.
8. **Historical note, so it is not rediscovered as a mystery.** `figma.ui.resize` had a regression
   in early 2026 where it also repositioned the plugin window. Figma confirmed and fixed it.
