# LS-23 — Calibrate expansion bands against real translations

Issue: [LS-23](https://linear.app/brilliant-solutions/issue/LS-23). Evidence and full tables:
`docs/expansion-calibration.md`. Reproduce with `node scripts/measure-expansion.mjs`.

This issue changes **values, not structure**. The model stays
`ratio = 1 + bandGrowth(sourceLength) × languageFactor(language)`, and `expansionRatio` remains the
single calibration edit point, exactly as the issue requires.

---

## §1 Contracts

**Consumed, never redefined (agent-guidelines §4)** — nothing new. LS-23 edits constants inside a
module it owns.

| Symbol | Owner | Module |
|---|---|---|
| `padToLength` | LS-8/LS-10 | `src/common/pseudoloc.ts` |
| `expandForLanguage`, `isUnsupportedLanguage` | LS-8 | consumed by `src/main/overflow/index.ts` |

**Owned and changed by LS-23**, all in `src/main/overflow/expand.ts`:

- `LENGTH_BANDS` growth values and `FINAL_BAND_GROWTH`
- `LANGUAGE_FACTORS` values (keys unchanged)

**Deliberately unchanged:**

- `UNSUPPORTED_LANGUAGES` — CJK/Thai stay refused. A character-count model is wrong for those
  scripts regardless of calibration, and no amount of corpus data fixes that (LS-8.1 §2).
- `DEFAULT_LANGUAGE_FACTOR` stays `1.0`, and the fit is anchored to keep that meaningful (§2.4).
- `LENGTH_BANDS` boundaries (10/20/30/50/70). The banding *shape* is confirmed by the data — short
  strings do grow proportionally more, in all twelve languages — so only the growth values moved.
- `transform()` (pseudo-loc) takes a user-chosen `expansionPct` and never consults `LENGTH_BANDS`,
  so LS-10's output is unaffected. The two issues need no sequencing in either direction.

**§1.2 Upstream amendments required:** none.

## §2 Resolved Defaults

### §2.1 The model tracks the 90th percentile of observed growth

**Decided (2026-09-13).** A flagged string is one that overflows *in the worst 10% of plausible
phrasings*. This is a product judgement, not something the data settles — the measurement can say
what growth looks like, not which part of the distribution a warning should fire on.

p90 rather than the mean, because band-1 German growth has mean 0.351 and p99 2.500: the
distribution is heavily right-skewed and the tail is real (`Redo` → `Wiederherstellen` is +300%).
The mean would protect against almost no real phrasings. p90 rather than p95/p99 because the whole
complaint in the issue is over-flagging, and each step up the tail buys coverage at a rising cost in
candidate length.

### §2.2 Band growth values

| Band | was | now |
|---|---|---|
| 1–10 | 1.50 | **1.04** |
| 11–20 | 0.90 | **0.73** |
| 21–30 | 0.70 | **0.61** |
| 31–50 | 0.50 | **0.49** |
| 51–70 | 0.35 | **0.41** |
| 71+ | 0.30 | **0.37** |

The old table was **mis-sloped, not uniformly too high**. Band 1 over-reserved by roughly 2× (the
German candidate averaged 2.36× the real translation's length), while bands 5 and 6 sat *below*
observed p90 and were quietly missing real overflow — coverage there was 79% for German and 62% for
French. Both ends move, in opposite directions.

### §2.3 Language factors

| | was | now | | was | now |
|---|---|---|---|---|---|
| fr | 0.95 | **1.13** | it | 0.90 | 0.98 |
| ru | 1.05 | 1.12 | es | 1.00 | 0.97 |
| pl | 1.05 | 1.04 | nl | 1.10 | 0.92 |
| de | 1.15 | 1.03 | fi | 1.20 | **0.83** |
| pt | 0.95 | 1.01 | tr | 0.85 | 0.70 |
| | | | ar | 0.85 | **0.34** |
| | | | he | 0.85 | **0.31** |

Two corrections are large and counter-intuitive, and both replicate across all three corpora:

- **French and Finnish swap ends of the table.** On total character count French is the most
  expansive language in the set and Finnish one of the least — the reverse of the old ordering.
- **Hebrew and Arabic drop to ~0.3.** Their translations are barely longer than English, and in the
  long bands not longer at all (Arabic's p90 growth is *negative* above 50 characters). At 0.85 the
  model reserved more than twice what those languages need.

**German's reputation is not wrong, it was attached to the wrong quantity.** German grows its
longest *unbreakable token* by +129% at p90 against French's +71% — and a fixed-width container
breaks on the longest token it cannot wrap. But this factor multiplies *total length*, where German
is the milder of the pair. Correcting it downward here is right for what the factor does; the
wrapping dimension is a separate mechanism, filed as **LS-27**.

### §2.4 Bands and factors are fitted together, not in sequence

A rank-1 approximation of the twelve-locale × six-band p90 grid, solved by alternating least
squares. Fitting bands first and factors afterwards would bake the old, wrong factors into the new
band values — and since the old factors are exactly what this issue found to be wrong, that ordering
would have silently preserved the defect.

**Linear space, not the obvious log-space additive fit.** Arabic and Hebrew have observed p90 growth
of zero or slightly negative in the long bands, and `log(0)` is undefined. That is a real property
of those languages, not bad data, so the fit tolerates it rather than excluding them.

**Anchored so the European factors have geometric mean exactly 1.0**, which preserves the meaning
`DEFAULT_LANGUAGE_FACTOR = 1.0` already claims ("European average"). An unrecognised tag therefore
still gets an average-European reserve rather than an arbitrary one.

### §2.5 What the change buys

| | before | after |
|---|---|---|
| coverage spread across 12 locales | 86.8% – 99.3% | **89.5% – 93.9%** |
| mean candidate / actual length | 1.72× | **1.47×** |
| worst-covered locale | 86.8% (fr) | **89.5%** |

Coverage *falling* in an over-reserved locale is the intended correction, not a regression: the fit
targets p90 everywhere, so Hebrew moving from 99.1% to 93.9% is the model no longer reserving twice
what that language needs. The honest summary is that coverage becomes **consistent** — a 12.5-point
spread collapses to 4.4 — while over-reservation falls in every single locale.

The issue's worked example, German `"Extract"` (real translation `Extrahieren`, 11 characters):
candidate **20 → 15**.

### §2.6 The residual budget is measured, not chosen

One band table × one scalar factor cannot fit twelve languages exactly. Residuals stay within ±0.10
for most cells; the largest are band 1 for the outliers (`ar` −0.21, `he` −0.18, `fr` +0.18). The
±0.25 bound asserted in §3 is that measured approximation error, not a tolerance picked to make a
test pass. Tightening it requires per-language band tables, which the issue explicitly scopes out
and which now have the data to be reconsidered.

## §3 Concrete Acceptance

### §3.1 The calibration guard

`src/main/overflow/expand.test.ts` asserts the shipped constants against
`fixtures/expansion-p90.json` — the observed p90 grid, regenerated by
`node scripts/measure-expansion.mjs --fixture`. This satisfies the issue's fourth success criterion:
the band values are checked **against the recorded data** rather than restated from the source table.

The fixture records only the *observed* grid, never the fitted table, so the test cannot be
satisfied by a table that merely restates itself.

Asserted:

1. the sample is what it claims (p90 target, >100,000 pairs, three corpora, and every calibrated
   language present in the measurement — no unmeasured entries in `LANGUAGE_FACTORS`);
2. worst-case residual ≤ 0.25;
3. mean absolute residual ≤ 0.08;
4. **non-vacuity** — the same check re-run against the superseded pre-LS-23 table must breach the
   bound.

Verified by deliberate breakage, per agent-guidelines §6: reverting band 1 to 1.50 fails the guard,
and reverting *only* the French factor to 0.95 fails exactly one test — the calibration guard, which
no restated-value test would have caught.

### §3.2 Rebaselined pinned values

The LS-10 no-regression guard and the `expandForLanguage` length assertions pin exact output, so
they move with the calibration. Recomputed from the implementation rather than hand-derived — the
lesson from LS-10 §3.2, where three hand-computed values were wrong. Their purpose is unchanged:
they still forbid these strings moving as a side effect of work on `transform` or `padToLength`.

### §3.3 Not covered by Vitest

**The design-file flag rate.** The issue's third success criterion — re-measure against the 34%
baseline — needs a scan of a real file in Figma and cannot be asserted in Vitest. **Measured
2026-09-14** via the A/B harness: 41.1% → 39.2% on identical nodes. See §5.1, which is the more
important result: the flag rate turned out not to be calibration-bound at all.

**`fixtures/overflow-spike.fig`.** The `autoheight-maxlines` row was width-tuned so a 41-character
candidate needed 3 lines at 140px; the candidate is now 36. The reasoning should still hold — the
padding adds no spaces, leaving a 24-character unbreakable token that cannot fit 140px — but a
layout prediction is only settled by Figma. Flagged in `generateOverflowSpike.ts` for the next LS-8
acceptance pass.

## §5 Carry-forward

1. **The flag rate is not calibration-bound, and no issue holds this yet.** The A/B harness
   (`src/main/overflow/calibration.ts`) measured both tables against the same 569 nodes of the
   LocaleSync design file, German, 0 un-measurable:

   | band | nodes | old flagged | new flagged |
   |---|---|---|---|
   | 1–10 | 202 | 139 (68.8%) | 136 (67.3%) |
   | 11–20 | 135 | 40 (29.6%) | 37 (27.4%) |
   | 21–30 | 128 | 14 (10.9%) | 14 (10.9%) |
   | 31–50 | 46 | 9 (19.6%) | 4 (8.7%) |
   | 51–70 | 18 | 14 (77.8%) | 14 (77.8%) |
   | 71+ | 40 | 18 (45.0%) | 18 (45.0%) |
   | **total** | **569** | **234 (41.1%)** | **223 (39.2%)** |

   **Cutting band-1 reserve by 38% removed 3 flags out of 139** — an elasticity of −2.2%, on the
   band that is 61% of all flags. Those nodes overflow under any plausible ratio, so the expansion
   ratio is not what drives the flag rate on this file. The issue's premise was right that the
   values were wrong (proven independently against the corpus) and wrong that the values *cause*
   the over-flagging.

   The 34% baseline is not comparable to either column: it was a partial scan ("135 issues in the
   first 400 nodes") of a 485-node file that has since grown to 569. The old table on today's file
   reads 41.1%, so the apparent rise is the file changing, not the model.

   **Probably true positives.** The design file is a ~400px mockup of the plugin's own UI, and its
   five-tab bar overflows 25px/11px/7px in German — containers drawn snug to English text overflow
   at any ratio. If so, "a 34% flag rate on a file that is not broken" was itself the wrong framing.
   The measurement that settles it is the `overflowPx` distribution among band-1 flags: mostly 20px+
   means real breaks and the engine is correct; mostly 1–3px means the model is marginally tipping
   nodes over, which is a different defect class from calibration. **Deliberately not filed as an
   issue yet (2026-09-14) — recorded here so it is not lost.**
2. **LS-27** — the wrapping dimension (longest unbreakable token), measured here and deliberately
   not acted on.
3. **Per-language band tables.** The issue scoped these out pending data. The data now exists, and
   §2.6's residuals show exactly where one shared table strains: band 1 for Arabic, Hebrew and
   French. Worth revisiting only if those residuals prove to matter in practice.
4. **Corpus refresh.** `fixtures/expansion-p90.json` records `sha256` prefixes per catalogue. The
   values will drift slowly as upstream translations change; the guard's ±0.25 budget absorbs that,
   and a refresh is only needed if it starts failing.
